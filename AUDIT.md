# UFC Prediction Codebase Audit

Audit date: 2026-08-15

## Executive conclusion

The largest prediction problem is not the choice of classifier. It is the
point-in-time integrity of the training table and the evaluation design. The
original random split reports 63.8% accuracy and 0.636 log loss, but the same
feature set falls to 59.6% and 0.706 on the newest 20% of the committed data.
After the sanitizer fixes, split decisions, and the August catch-up are
included, the isolated end-to-end run scored 52.8% and 0.697 on its temporal
holdout. That is not evidence of a reliable current betting edge.

The largest automation problem was a chain of independent failures:

1. `bokeh` was imported but absent from `requirements.txt`.
2. UFCStats now returns a JavaScript proof-of-work page with HTTP 200 to a bare
   request, so the old parser dereferenced a missing table.
3. FightOdds used a fixed sleep and positional table lookup.
4. The public repository workflow was disabled after 60 days of inactivity.
5. The commit step failed on legitimate no-change runs and staged the entire
   repository, including generated bytecode.

The patch in this worktree addresses those immediate blockers. A complete
update was also run against a disposable copy: it caught up eleven completed
cards in 16m59s, deferred a same-day unfinished event, produced 17,598 valid
derived sides, and passed strict validation. A subsequent steady-state run
changed zero files in the workflow commit scope.

## Highest-priority remaining issues

### 1. Fighter identity must use source IDs, not names

Stable UFCStats URLs already exist, but feature joins still use fuzzy names.
This creates real collisions:

- Two different UFCStats fighters are named Bruno Silva.
- All recent Bruno Silva rows have missing derived features because the master
  lookup cannot choose one record.
- `fighter_stats.json` is keyed by display name and silently loses one Bruno.
- Suffix removal conflates people such as Lance Gibson Jr. with his father.
- Renames such as Kai Kamaka III no longer match the stale master name.

Carry `event_id`, `fight_id`, `fighter_id`, and `opponent_id` through raw,
derived, forecast, result, and website tables. Names should be display fields.
Resolve third-party odds names through a reviewed alias table that maps to IDs
and rejects non-unique matches.

### 2. Rebuild prediction history from immutable facts

Of 1,093 dated history records matched to raw outcomes, 51 stored `correct?`
values disagreed with the result: 22 draws/no-contests, 8 even-money forecasts,
and 21 ordinary winner/loser inversions. Another 397 of 1,491 rows have no
date. The previous code also deleted blank predictions and unmatched fights,
which made reported accuracy conditional on successful coverage.

Store forecasts immutably with fight ID, raw and calibrated probability,
prediction timestamp, model version/git SHA, training cutoff, odds timestamp,
and abstention reason. Join results by fight ID and derive correctness on read.
Keep canceled, postponed, draw, no-contest, unmatched, and no-prediction rows.

### 3. Make the market the required benchmark

On 312 completed forecasts with usable two-sided book quotes, no-vig consensus
outperformed the model on the same fights:

| Metric | Stats model | Book consensus |
|---|---:|---:|
| Accuracy | 64.95% | 69.87% |
| Log loss | 0.641 | 0.587 |
| Brier score | 0.224 | 0.201 |
| AUC | 0.703 | 0.750 |

This sample is selected and the odds have no collection timestamps, so it does
not prove a durable market edge. It is enough to require market-only as the
baseline. A strong next design is:

`logit(p_fight) = logit(p_no_vig_market) + residual(stats, form, matchup)`

Keep the residual model only if it improves rolling out-of-time log loss over
market alone.

### 4. Replace one temporal holdout with nested rolling evaluation

Use event-grouped rolling-origin folds. Fit imputation, scaling, feature
selection, calibration, and hyperparameters inside each training fold. Report
log loss and Brier score first, followed by calibration slope/intercept, ECE,
AUC, accuracy, coverage, and card-block bootstrap intervals. Refit the frozen
pipeline on all eligible history only after evaluation.

Useful baselines, in order:

1. 50% and division priors.
2. Elo or Glicko with inactivity/uncertainty.
3. Regularized logistic regression.
4. No-vig multi-book consensus.
5. Market plus a regularized stats residual.
6. Shallow gradient boosting/CatBoost.

With only roughly 5,000 recent labeled fights, a neural network is not the
first opportunity.

### 5. Improve point-in-time features before model complexity

Prioritize:

- Elo/Glicko and opponent-strength adjustment.
- Exponentially decayed form instead of hard one/three/five-year windows.
- Prior fights/minutes and explicit uncertainty for sparse/debut fighters.
- Layoff, age curve, division/weight-class change, scheduled rounds/title
  status, and stance matchup.
- Market log-odds and line movement captured at forecast time.

Add a prefix-invariance test for every historical feature: appending future
events must never change an existing feature row.

### 6. Unify the Python and browser predictors

The weekly model uses 30 scaled features. The browser still uses a separate
14-feature coefficient vector and does not load the Python scaler. Its ISO
date parsing and future-row bugs have been repaired, and the UI is now marked
as experimental, but it remains a different model.

Persist one versioned artifact containing feature order, imputer, scaler,
model, calibrator, training cutoff, and version. Serve that exact contract to
both weekly predictions and the website, or remove the custom browser model.

### 7. Reduce repository and feature-build churn

The working tree is about 716 MB, `.git` packs are about 1.06 GiB, and the
repository tracks caches/checkpoints and duplicate large notebooks. The
catch-up recomputed 422 complete fighter histories and took almost 17 minutes.

Untrack existing `__pycache__`, `.pyc`, `.ipynb_checkpoints`, and `.DS_Store`
files in a separate cleanup commit. Move immutable raw snapshots/model
artifacts to release/object storage or Git LFS if appropriate. Materialize
features by stable fight ID and update only affected fighters/dependencies.

## Reliability and sanitation implemented here

- Central UFCStats client with timeouts, retries/backoff, rate limiting,
  proof-of-work handling, HTTP checks, and page-content contracts.
- All-or-nothing event ingestion, recent event-manifest reconciliation,
  fight/fighter URL deduplication, correct draw/no-contest parsing, stable date
  sorting, and atomic CSV/JSON replacement.
- Structural validator for schemas, source IDs, doubled-pair symmetry,
  complementary results, numeric domains, landed/attempted relationships,
  raw/derived reconciliation, freshness, and upcoming-card dates.
- Correct per-fight second-degree time windows and future-row invariance tests.
- Split decisions retained; missing selected values explicitly imputed; model
  orientation deterministic and antisymmetric; temporal evaluation used; final
  model refit on all eligible history.
- Fractional Kelly at 25% with a hard 5% per-side cap. This is only a safety
  guard, not evidence that betting is profitable.
- FightOdds uses explicit waits and Selenium Manager, aggregates de-vigged
  probabilities rather than American lines, swaps reversed matchups correctly,
  and degrades to explicit unavailable/unmatched status.
- History retains no-prediction/unmatched rows and treats draws/no-contests as
  unscored/void rather than losses.
- GitHub Actions now has current actions, Python 3.11, dependency caching,
  tests, pre/post validation, write permission, concurrency control, a timeout,
  a manual dispatch trigger, scoped staging, rebase-before-push, and a no-op
  commit guard.

## Deployment checklist

1. Review and commit this worktree; generated production data was deliberately
   not changed during the audit.
2. Push the workflow change to the default branch. Changing its cron schedule
   should reactivate an inactivity-disabled schedule; if GitHub still shows it
   disabled, use **Actions → Update UFC data → Enable workflow** once.
3. Use **Run workflow** once to perform the backlog update and inspect the
   strict validator output.
4. Confirm the first bot commit contains only processed/external data and
   Bokeh plots—not bytecode, notebooks, or unrelated files.
5. Treat current predictions as experimental until rolling market-relative
   evaluation shows a repeatable, calibrated out-of-time improvement.
